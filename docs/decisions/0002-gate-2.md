# 0002 — Gate 2 decisions

Status: accepted. Date: gate 2.

Decisions taken while completing PhantomBench-12, the replay engine, the
metrics and the fair baseline infrastructure.

## Eleven fixtures are generated; PB-A03 stays hand-authored

`scripts/generate-fixtures.ts` builds every case except `PB-A03` from a compact
spec, and produces `final-state.json` by replaying the trajectory. That makes
"the final state is derivable from the initial state and the successful write
events" true by construction rather than by careful typing.

**The circularity is real and worth naming.** The generator and the validator
share the replay engine, so the replay check cannot catch a mistake in the
engine itself — it catches later hand-edits and drift. What independently
establishes that a case means what it claims is the hand-authored gold
contract, gold verdict and metadata, plus the approved-matrix registry that all
three are checked against. `PB-A03` remains hand-authored end to end, and the
replay reproduces it byte for byte without a single edit to the Gate 1 fixture,
which is the strongest evidence available that the engine is faithful.

## Mutation timestamps come from the `tool_call` event

Effects stamp `updatedAt` / `sentAt` / `executedAt` from the timestamp of the
call, not the result. That choice was forced by `PB-A03`, which was written
before the engine existed: it is the reading under which the frozen fixture
replays exactly. It is also the more defensible one — the mutation happens when
the action is taken, not when the acknowledgement arrives.

## A requirement is a conjunction; two new assertion kinds

Two capabilities the canonical templates need:

- `record_field_equals_selected_record_id` proves a *relationship* — "the
  receipt references the completed refund" — without naming a generated id. A
  contract compiled before the run cannot know `REF-8811`, so a contract that
  hardcodes it is not a contract the Contract Agent could ever produce. `A-OUT-02`
  and `B-OUT-02` use it. `PB-A03`'s frozen gold contract keeps its literal-id
  form, which is why both shapes are exercised.
- `record_array_contains_exact` checks a required note without comparing whole
  arrays or asking a model to judge similarity. Matching is literal: no case
  folding, no trimming, no substring.

Both return `indeterminate` on an ambiguous selector or a missing collection,
and `violated` when the data is present and wrong.

## Event selectors are validated by combination, not just by shape

`status` on a `tool_call`, `scope` on an `agent_message`: schema-valid,
semantically meaningless, and they would match nothing while reading like a
passing check. Now rejected at parse time. This matters most for the model-
generated contracts of Gate 3, before they exist rather than after.

## The prediction phase cannot reach gold data

The baseline runner imports the agent-visible loader and the split list, and
nothing else. Gold is loaded by `score.ts`, after the prediction artifact is on
disk. A test registers an observer on every guarded case-file read and asserts
that no human-only file was opened while the prediction file did not yet exist.

Writing that test changed the design. The runner originally took a
gold-inclusive `datasetHash` computed by its caller — before any prediction
existed. The manifest now records a fingerprint of the agent-visible content
only, and the gold-inclusive dataset hash is written by the scoring report.

## The baseline sees six inputs and no metadata

Task instruction, final response, trajectory, both state snapshots, and
descriptions of the read-only tools. It never sees a case id, a split label, a
requirement id, or the case matrix. Tests assert the rendered prompt contains
none of them.

The prompt is frozen at `prompts/baseline-evaluator/v1.md` and hashed into
every manifest. It is a genuine attempt at the task, not a weakened strawman:
StateProof has to earn its margin through typed contracts, evidence linking and
deterministic checks.

## Temperature is recorded as null, and effort is what is fixed

The fairness rules require temperature, max tokens and timeout to be fixed in
configuration. The current Claude models reject a sampling temperature
outright, so `temperature: null` is recorded explicitly — stating that the knob
does not exist beats leaving it unmentioned — and reasoning effort is fixed at
`high` instead, alongside max tokens and timeout. The same client configuration
will serve the StateProof agents, so the constraint binds both systems.

## No credentials means no run, not a simulated one

`pnpm benchmark:baseline` exits non-zero with an actionable message when no key
is configured, and writes nothing. The deterministic fake client exists only
for tests and is unreachable from the CLI. A report with no model behind it
would be worse than no report.

The locked split is refused unless `STATEPROOF_ALLOW_LOCKED_RUN=1` is set, so
an intermediate run cannot spend the one comparison the challenge cases exist
for.

## An unparsed prediction is scored, not dropped

If a case never produces schema-valid output after its one repair retry, it is
recorded with `prediction: null` and scored `NEEDS_REVIEW`. That is incorrect
under Balanced Verdict Accuracy and is *not* an unsafe false completion. It
stays in the denominator: dropping it would quietly improve the score.

## Still deferred

- Structured outputs (`output_config.format`) as a robustness layer. The
  prompt-plus-Zod-plus-repair path is what the prompt pack specifies and has no
  unknowns; adding schema-constrained decoding is a later robustness change
  that must be applied to the baseline and StateProof together.
- Estimated cost in USD. Recorded as `null` until a live run produces real
  token counts to price.
- `packageLockHash` in the manifest, currently `null`.
- Reconstructing state for domains beyond refund-operations; the replay engine
  is deliberately domain-specific.
