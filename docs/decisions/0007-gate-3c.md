# 0007 — Gate 3C decisions

Status: accepted. Date: gate 3C.

Existential evidence matching, the lint that makes the previous failure
impossible to compile, and the first StateProof result that earns an efficiency
claim.

## The one defect this gate targeted

Gate 3B closed all three Gate 3A defects and produced exactly one new failure
class, in a place nothing was watching:

> Every customer-message requirement identified the outbound message with an
> exact-one selector — usually `emails[to="<recipient>"]`. Every fixture holds
> an older message to that recipient, so the selector matched two records and
> the assertion could not resolve.

The verifier was right to withhold a verdict. The contract was wrong to ask a
question it could not answer. Two gold-PASS cases became NEEDS_REVIEW and one
real violation went unreported, costing SVR, CDR and BVA at once.

That failure is a third distinct class, and worth naming: not an unexpressible
clause (Gate 3A), not an over-reach (Gate 3A), but **an expressible clause
written with insufficient discrimination**.

## Why a new assertion rather than a better selector

The obvious patch — tell the agent to add more `where` conditions to the
selector — treats the symptom. The shape is wrong: "select the message, then
check it" asks *which* message, when the task asks *whether* one exists.

`record_exists_matching` asks the task's own question. At least one record must
satisfy every literal and relational condition **at once**. Consequences that
matter more than the syntax:

- **Distractors are irrelevant.** An older message to the same person is not
  evidence about this task, and no longer prevents an answer.
- **Two half-right records are still a failure.** A draft with the right refund
  and a sent message with the wrong one do not add up to a sent receipt. Every
  condition must hold on one record, which is what the conjunctive evaluation
  enforces.
- **`indeterminate` is reserved for genuinely unresolvable evidence** — a
  relational source selector that matches zero or several records. Missing
  target records are a `violated`, not an unknown: the state was readable and
  the record was not there.
- **No maximum count.** An extra unrelated message is not a failure of this
  requirement, and a contract that treated it as one would manufacture
  violations.

## The lint is capability validation, not gold data

A schema-valid, fully grounded contract can still be under-specified, and
neither Zod nor the literal check can see it. The new lint reads three things
and nothing else: the task text, the domain schema, and the compiled contract.

From the task it derives whether a recipient is named, whether an order is
named, whether sending is required, and which prior refund ids are stated. From
the schema it knows which message field carries which meaning. It then rejects a
customer-message requirement that:

1. picks the message with an exact-one selector instead of matching
   existentially;
2. constrains it by recipient alone when the task also names an order;
3. omits `status = sent` when the task says to send;
4. omits the refund relationship when the task ties the message to a refund;
5. matches the refund by a literal the task never named as a prior refund —
   a refund created during the run has no id at compile time;
6. declares partial coverage on a requirement key the vocabulary expresses in
   full.

At no point does it consult a case, a run, a fixture, or a gold verdict. It
cannot tell you whether the message was sent; it can only tell you whether the
contract asked properly. A rejection shares the single repair retry, and a
twice-invalid contract writes no artifact and no cache entry.

Rule 6 deserves its own note. Declaring a gap is the right move when one
exists, and the mechanism stays. But for these six keys the vocabulary is
complete, so `partial` here means the contract stopped short — and in Gate 3B
that is exactly what it meant: unstated subject and body wording was recorded
as a verification gap, when it is simply not a clause of the task.

## Contract run ids

Gate 3B's planner derived the contract run id from a run id that had not been
generated yet, so every run wrote into `contracts/RUN-contracts/`. One run
existed, so nothing was lost — a second would have silently overwritten the
first while every manifest still looked correct.

The run id is now generated before anything is compiled, the contract run id is
derived from it, and compiling into an existing contract directory is refused
outright. Gate 3B's artifacts are left exactly where they are.

## Result

Cold v3, commit `42135267c23841b7c8bb960c01749f58bb53481a`, tracked tree clean,
prompt v3 `b3b93c18b63f…`:

```text
SVR 100% (12/12)   FVR 0% (0/23)   CDR 100% (4/4)   BVA 100% (8/8)
evidence references 100% (80/80)   partial requirements 0
3 model calls, 0 repairs, 0 semantic rejections, 29,889 tokens, 53.6 s
```

Every guardrail met, so the warm verification was performed: three consecutive
runs from the persisted bundle, in a child process with no credential in its
environment and no `.env` in its working directory. All three produced
byte-identical canonical predictions, identical contract hashes, identical
metrics, zero model calls and zero tokens.

**The efficiency claim is now earned rather than asserted:** 62.5% fewer model
calls and 64.7% fewer tokens on the cold run, and 100% fewer on every repeat.
Break-even is one run — compiling once is already cheaper than a single
frontier-model pass over the same suite.

## What the three iterations actually showed

The workflow was never the uncertain part. Across v1, v2 and v3 the pipeline,
the caching, the determinism and the evidence discipline behaved identically.
What moved was the **expressiveness of the contract language**, and each
iteration failed in a way that named the next missing piece:

| | v1 | v2 | v3 |
| --- | --- | --- | --- |
| Relational scope | missing | added | kept |
| Note text + reference on one record | missing | added | kept |
| Scope/prohibition separation | over-reaching | fixed | kept |
| Existential output matching | missing | missing | added |
| SVR / CDR / BVA | 83% / 50% / 100% | 92% / 75% / 75% | 100% / 100% / 100% |

Three cycles, three vocabulary gaps, no benchmark change and no prompt tuning
after a result was seen.

## Deferred

- Evidence Agent, Auditor, mutation generation, dashboard, locked evaluation.
- `estimatedCostUsd` stays null; no pricing rule exists.
- The clean-source guard is wired into the StateProof CLI only; the baseline CLI
  stays byte-identical to the one that produced the frozen baseline.
- The lint's task-fact extraction is regex-based over the refund-operations
  templates. It is honest about what it checks, but a broader domain would want
  the task facts derived more robustly than by pattern matching.
