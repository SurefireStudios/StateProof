# 0003 — Gate 2.5 decisions

Status: accepted. Date: gate 2.5.

Source-audit corrections applied before the first real baseline run.

## Gold isolation is now a package boundary, not a claim

Gate 2 said gold was unreachable "by module graph", but the package root
exported both loaders, so the claim was not true. `@stateproof/benchmark` now
has three entry points:

| Entry point | Contains |
| --- | --- |
| `@stateproof/benchmark` | paths, guarded agent reader, split membership, agent-visible loaders |
| `@stateproof/benchmark/gold` | `createGoldReader`, `loadGoldBundle`, `loadBenchmarkCase`, `loadAllCases`, `datasetHash` |
| `@stateproof/benchmark/validate` | the fixture validator |

A test imports the root and asserts every gold name is absent from it. The
prediction runner imports only the root; the scoring layer imports `/gold`
explicitly, with a comment saying why it is allowed to.

The read-observer test from Gate 2 still stands alongside it: the boundary
proves *what can be imported*, the observer proves *what was actually opened*.

## PB-A03 is no longer hand-authored

It was frozen after Gate 1, and it drifted: `A-OUT-02` kept a hardcoded
`REF-8801` while the other Template A cases moved to the relational reference.
A contract compiled before a run cannot know a generated id, so the frozen
shape was one no Contract Agent could ever produce.

`PB-A03` is now generated like every other case, with its irregular
hand-authored timestamps preserved through an explicit timestamp override on
the trajectory builder. Its agent-visible hash is unchanged — `ccb483bdd838`
before and after — so the demo case is byte-equivalent while its gold contract
now matches its siblings.

`validateContractConsistency` is what stops this recurring: cases of the same
template must share requirement ids and assertion-kind shapes, and a one-off
drift is now an error rather than something a human has to notice.

## Two Template C requirements were quietly satisfiable

- **`C-OUT-02`** used two separate `record_array_contains_exact` assertions,
  one for the note text and one for the refund reference. Two *different* notes
  could satisfy them, so a case where no single note carried both would have
  passed. Now one assertion with both matchers in its `element`.
- **`C-OUT-01`** identified the notice only by its order, so any sent email to
  `lee@example.com` about `ORD-3091` counted. The task names `RF-8801`
  explicitly — this is not a generated-id problem — so the notice is now
  selected by `relatedOrderId` *and* `refundId`, and an unrelated message
  cannot stand in for it.

Both have regression tests built from decoys that would have passed before.

## Replay effects are transactional

`applyRefundExecute` created the refund record before validating the order's
money fields, so a currency mismatch could return failure having already
inserted a refund. Each write now runs against a clone and commits only if the
whole effect — including the touched-entity check — succeeds. A test asserts
that a currency mismatch leaves `refunds` empty, which it did not before.

## A report covers exactly the split it claims

Before scoring, the prediction file must contain exactly one entry for every
case in its declared split. A missing case shrinks the denominator, a duplicate
double-counts a verdict, and a case from the other split is a locked-data leak
— all three would move a headline number without being visible in it. Scoring
refuses rather than reporting.

## The manifest has two dataset hashes, deliberately

`agentVisibleDatasetHash` is written by the prediction phase and covers only
what the model was shown. `datasetHash` is gold-inclusive, starts as `null`,
and is filled in by the scoring phase along with `reportPath`. Keeping them
separate is what lets the prediction phase record real provenance without
opening a gold file. `packageLockHash` is now a real sha256 of `pnpm-lock.yaml`.

## `.env` actually works now, under a separate credential name

The credential message told people to use a `.env` the CLI never read, and
suggested `ant auth login`, which the SDK adapter does not support. `.env` is
now loaded explicitly via a pinned `dotenv`, and the message names only the
mechanism that works.

More importantly, StateProof reads **`STATEPROOF_ANTHROPIC_API_KEY`**, never
`ANTHROPIC_API_KEY`. This repository is developed with Claude Code, which uses
`ANTHROPIC_API_KEY` for its own subscription authentication; sharing the name
would let a project key silently take over the developer's session and bill
their work to the wrong place. The value is passed straight to the SDK client
as `apiKey` and is never copied into the ambient environment, so the SDK cannot
fall back to a variable we did not intend it to see.

`.claude/settings.local.json` additionally denies `Read(.env)` and
`Read(.env.*)`, so the assistant working in this repository cannot read the
secret file even by accident. StateProof's own process still loads it when a
human runs a benchmark command.

`STATEPROOF_MODEL_ID`, `_EFFORT`, `_MAX_TOKENS` and `_TIMEOUT_MS` override the
defaults and are recorded at their actual values in the manifest, so a result
can never be attributed to the wrong configuration.

The key is read at client construction and never enters the recorded
configuration, an artifact, or stdout. A test asserts no credential name or
value appears in a written manifest.

## `pnpm benchmark:smoke-model`

One tiny structured request against the configured provider, so a bad API
configuration surfaces in seconds rather than eight cases into a real run. It
imports no benchmark module and writes nothing; tests assert both.
