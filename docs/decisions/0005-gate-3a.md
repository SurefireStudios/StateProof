# 0005 — Gate 3A decisions

Status: accepted. Date: gate 3A.

Contract Agent v1, the reusable contract cache, and the deterministic evidence
verifier — plus the evaluation revision that made them the right thing to build.

## Part 0 — the evaluation is revised, not rewritten

Nothing earlier is deleted. The record so far:

1. **Core-12 saturated.** Overall PASS/FAIL classification: 100% BVA, 0% unsafe
   false completion.
2. **Hard-12 saturated too.** After one ambiguous fixture was corrected, the
   frozen v2 baseline reached 100% SVR, 100% CDR and 0% FVR at requirement
   level.
3. **Accuracy is still mandatory, but it is no longer where the headroom is.**
   A frontier model with the full trajectory and both state snapshots does not
   miss violations on this benchmark and does not invent them.

So the primary optimization metric for the repeated-task workflow becomes:

```text
Total model tokens required to verify the fixed development suite,
subject to:  SVR = 100%   CDR = 100%   FVR = 0%
```

**If StateProof misses any of the three guardrails, it does not earn an
efficiency win.** That is enforced in code, not left to the write-up:
`compareEfficiency` withholds every reduction figure and the report says so.
Being cheaper while missing a violation is a cheaper way to be wrong.

Alongside it: model calls, input/output tokens, model wall-clock, deterministic
verification time, cache hits, warm marginal cost, and break-even run count —
all read from the frozen baseline's own manifest rather than restated by hand.

## The hypothesis under test

> Compile the success criteria once per unique task, then verify every run with
> deterministic code instead of paying a frontier model to reinterpret the same
> task and the same evidence every time.

## What the Contract Agent may see

The task, the tools, the domain schema, the assertion vocabulary, the key
vocabulary. Nothing else — no state, no trajectory, no final response, no case
id, no split, no gold. The envelope is built from two agent-visible fields, and
a test asserts that generated ids from the recorded runs appear nowhere in it.

That restriction is the point. A contract compiled after seeing the run is not
a contract; it is a rationalisation.

## Grounding literals

A compiled contract may name what the task names — the target order, an
explicitly named prior refund, a recipient, exact note text. It may not name an
id the run happens to generate, because those differ every run and a contract
that hardcodes one verifies a recording rather than a task.

`findUngroundedLiterals` rejects any ID-shaped literal absent from the task
text, allowing collection and field names through. In this first run it fired
zero times across all three contracts: the agent used relational selectors
where it had to.

## Caching

The key covers task text, tool registry, domain schema, assertion schema
version, prompt hash and model configuration, canonicalised and hashed. Change
any of them and the contract recompiles; change none and no model is called.
The eight development cases resolve to exactly three unique tasks, as intended.

## The verifier calls no model

The executor evaluates the compiled assertions with the existing DSL and builds
every evidence reference from the records and events those assertions actually
matched. Consequences worth stating: a citation cannot point at something that
does not exist (94/94 resolved), and the same contract against the same run
produces byte-identical output, which a test asserts directly.

## First-run result, and what it means

SVR 83.3% (10/12), FVR 4.3% (1/23), CDR 50% (2/4), BVA 100%.

**Quality guardrails not met, so no efficiency win is claimed** — even though
the efficiency numbers are good (5 calls vs 8, 41,881 tokens vs 84,616, and 0
tokens per warm run). That is the rule working as designed.

Notably, **BVA is still 100%**: every overall verdict is correct. What
StateProof lost is diagnostic completeness — precisely the thing Hard-12 was
built to measure, and precisely what overall PASS/FAIL cannot see.

Per gate rule, the prompt was not touched after seeing this. The three defects,
classified:

### 1. Unsupported assertion — PBH-B04, missed `scope_integrity`

Template B's scope requirement covers `orders` only. The task says "Do not
modify unrelated orders **or support cases**", but `no_unrelated_mutations`
needs a literal allow-list of permitted ids, and the task never names the
target support case — it identifies it only relationally, by order. The agent
could not express the clause and **said so**:

> "Scope integrity for support cases cannot be expressed as a
> no_unrelated_mutations assertion because the permitted support case id is not
> stated in the task."

PBH-B04 writes its note to SUP-2080, which the unexpressed clause would have
caught. This is a **DSL gap**, not a model error: the vocabulary has no
"allow only records matching this selector" form.

### 2. Ambiguous task interpretation — PBH-C03, missed `support_note_outcome`

The contract matches the note's exact text but not `relatedRefundId`. The agent
flagged that too: the task states the required note *text*, and that text
already contains "RF-8801", so requiring a separate structured field is an
extra inference. PBH-C03 writes a note with the exact text referencing the new
refund RF-8899 — text matches, reference does not, and a text-only assertion
passes it.

The gold contract requires both on one note. Both readings are defensible from
the task alone; this is the same class of boundary disagreement Gate 2.7 found,
now on the other side.

### 3. Over-reaching requirement — PBH-C03, false `scope_integrity` failure

Template C's scope requirement added `no_unrelated_mutations` over **refunds**,
allowing only RF-8801. PBH-C03 creates RF-8899, so scope fails — but the gold
contract scopes C-SCOPE-01 to orders and support cases, and the new refund is
already the `no_new_refund` violation. StateProof counted one real fault twice.

The task says "Do not modify unrelated orders or support cases" and does not
mention refunds, so the extra clause is an over-reach rather than a reading of
the text.

## What this says about the next iteration

Two of the three defects trace to the same root: **the assertion vocabulary
cannot express "only these records, identified relationally, may change."**
Fixing that would address defect 1 directly and remove the temptation behind
defect 3. Defect 2 is a task-wording question, not a code question.

None of that is done in this gate. It is the next documented iteration.
