# 0006 — Gate 3B decisions

Status: accepted. Date: gate 3B.

Assertion DSL v2, Contract Agent prompt v2, semantic rejection, and a contract
bundle that a later run can actually verify from — plus an honest audit of what
Gate 3A claimed versus what it had measured.

## Part 0 — what the Gate 3A audit found

Nothing from Gate 3A is deleted, edited, or re-run. Its artifacts stand as
written. Five things in them are less than they appeared, and saying so is
cheaper than being caught by it later.

1. **Reuse was in-memory only.** Gate 3A demonstrated that eight cases resolve
   to three unique tasks and that five of them cost no model call *within one
   process*. The CLI had no way to load a persisted contract on a later
   invocation, so the repeated-task claim was never exercised across runs — the
   form it would actually take in production.

2. **`warmMarginalTokens: 0` was a hypothesis, not a measurement.** It was
   emitted unconditionally, from the reasoning that a cached contract cannot
   cost tokens. The reasoning is sound and the number is probably right, but a
   figure nobody measured does not belong in a results table next to figures
   that were. Gate 3B removes the unconditional claim: the warm column is
   populated only from a completed warm-run manifest, and reads "not measured"
   otherwise.

3. **`cacheHit` was written as `false` for every case.** Five of the eight
   development cases reused an in-memory contract; the prediction file said
   none did. The compile step knew the truth and the run step overwrote it with
   a constant. Fixed: the first case using a newly compiled contract records
   `false`, every later case with the same fingerprint records `true`.

4. **`findUngroundedLiterals` recorded but never rejected.** The Gate 3A
   decision record says an ungrounded id "is rejected here rather than quietly
   producing a contract that only works once". In the code it was computed,
   stored on the artifact, and otherwise ignored — a contract naming an
   invented id would have been cached and used. It fired zero times, so no
   result is affected, but the documentation described a guard that did not
   exist. Gate 3B makes it a real rejection that consumes the repair retry.

5. **The Gate 3A live run predates its own commit.** Its manifest records the
   previous HEAD, so the commit it names does not contain the code and prompt
   that produced it. The artifact is kept as-is and labelled a development-run
   provenance limitation; it is not retro-fitted to look clean. From Gate 3B
   onwards a live run refuses to start unless the tracked tree matches HEAD.

## Part 0.4 — the clean-source rule

`inspectSourceTree` / `assertCleanSourceTree` refuse a live run when any tracked
file differs from HEAD, or when a non-artifact file is untracked. Generated
artifacts are exempt because they are outputs, and `.gitignore` already keeps
`.env` out of `git status`, so the guard never has to read or name it.

Every new manifest records the source commit, `sourceTreeClean`, the prompt
hash, and the assertion schema version. `checkPromptProvenance` re-derives each
prompt hash from `git show <commit>:<path>`, so the claim "this run used this
prompt" is checkable after the fact rather than asserted.

## Part 1 — the DSL gap that caused two of three defects

Gate 3A's root cause: **the vocabulary could not say "only records identified
relationally may change."** Template B's task scopes `orders` *and* `support
cases`, but never names the support case — it identifies it only as the one
belonging to the order. `no_unrelated_mutations` needs literal ids, so the
clause could not be written at all. The agent said so honestly and dropped it,
and PBH-B04's note to an unrelated case went unreported.

`mutations_limited_to` closes that: the allow-set is resolved from the state by
selector, at verification time. Three properties matter more than the syntax:

- **A selector that cannot name exactly one record is `indeterminate`, not
  `violated`.** Zero matches or three matches means the permitted set is
  unknown, and reporting a scope failure on that basis would be guessing. This
  is the same rule as everywhere else in StateProof: missing evidence never
  becomes a verdict.
- **Added, removed and modified records all count.** A scope clause that only
  noticed modifications would miss a record created in the wrong collection.
- **Evidence cites the diff, the permitted record, and every offending
  record**, so a failure points at what changed rather than merely asserting
  that something did.

### Declared coverage

The second half of the fix is admitting when the first half is not enough.
Every v2 requirement carries `verificationCoverage` and `limitations`. A
`partial` requirement can still FAIL on an implemented assertion, but can never
PASS — satisfying every implemented assertion earns NEEDS_REVIEW, and an
overall PASS is impossible while any must-pass requirement is partial.

This is deliberately asymmetric. A verifier that quietly drops what it cannot
express converts an unchecked obligation into a clean bill of health, which is
precisely the failure mode StateProof exists to catch in other systems.

## Part 2 — prompt v2, and what it is allowed to know

v1 is untouched and still loadable. v2 differs in four places, each traceable
to an observed defect rather than to a hunch: relational scope; scope covers
only the collections the task's scope clause names (a prohibition is never
duplicated into scope); one note must carry both its exact text and its
structured reference; and coverage must be declared.

It teaches a *policy*, not the benchmark. No case id, gold field, or expected
verdict appears in it, and the worked examples use placeholders rather than the
order ids of specific cases — a prompt that hardcoded `ORD-2077` would score
well here and be worthless on the next task. The input envelope is unchanged:
task, tools, domain schema, vocabularies, nothing else. The read-observer tests
still assert that generated ids from the recorded runs appear nowhere in it.

## Part 3 — semantic validation shares the repair budget

A schema-valid contract can still be unusable: an id the task never states, a
scope assertion selecting from the wrong collection, a coverage declaration
that contradicts itself. Those are now rejected before the contract is cached
or written, and the exact messages go back to the model as the single repair
retry — the same budget a schema failure gets, because a response that parses
but says something impossible is not a better outcome than one that does not
parse.

If the repaired response fails too, compilation fails: no artifact, no cache
entry, no verification against a contract nobody trusts. The raw attempts are
still written, so a rejected contract stays inspectable.

## Part 4 — bundles that verify themselves

The persisted bundle is a manifest plus one artifact per unique task, and
loading it re-derives every hash rather than believing the file: contract hash
recomputed from the contract text, cross-checked against the manifest's own
record; prompt, tool-registry and domain-schema hashes; assertion schema
version; provider, model and configuration; raw-response paths that must still
exist; and zero unresolved semantic violations.

Warm mode then recomputes each case's task fingerprint from the task in front
of it — never reading it from the artifact — and refuses to run if any case is
uncovered or any provenance field has moved. It **never compiles a miss**:
silently filling a gap would turn a measured warm run into a partly cold one
reported as warm.

## Part 5 — the cold v2 result, and the rule it triggered

One live cold experiment, commit `7cfb23ca366cb49917b6b069d69514e700c7c6ce`,
tracked tree clean, prompt v2 `880e3e23b6c3...`:

```text
SVR 91.7% (11/12)   CDR 75.0% (3/4)   FVR 0.0% (0/23)   BVA 75.0% (6/8)
evidence references 100% (114/114)    3 model calls, 0 repairs, 29,069 tokens
```

**Quality guardrails not met, so no warm run was performed and no efficiency
figure is claimed.** The protocol requires stopping there, and it was followed:
v2 was not touched after the result was seen.

All three targeted defects are closed. `mutations_limited_to` caught PBH-B04's
note to SUP-2080. The single `record_array_contains_exact` requiring both the
exact note text and `relatedRefundId` caught PBH-C03, which two decoy notes had
previously satisfied between them. Template C's scope no longer covers
`refunds`, so the duplicate refund is counted once and FVR fell to zero.

The failure is somewhere else entirely. Both the Template B and Template C
contracts selected the customer message by recipient alone —
`emails[to="maya@example.com"]`, `emails[to="lee@example.com"]` — and both
fixtures contain a pre-existing message to that address. The selector matches
two records, so the assertion is `indeterminate`: PBH-B01 and PBH-C01 become
NEEDS_REVIEW, and PBH-C03's genuine message violation is never reported.
Template A's contract filtered on `relatedOrderId` as well and is unaffected.

Two things follow, and they point in opposite directions.

**The verifier behaved correctly.** A contract that cannot tell which record it
means has not proven anything, and withholding a verdict is the right answer.
Turning that into a PASS would be the exact failure StateProof exists to catch;
turning it into a FAIL would be inventing a violation. `indeterminate` is not a
bug here.

**The contract was underspecified, and nothing checked for it.** Semantic
validation rejects ids the task never states, but has no notion of a selector
that will be ambiguous against real data — it never sees any data, by design.
Coverage declaration does not help either: the agent believed the requirement
was fully covered, and by its own reasoning it was. So the gap is a third kind
of defect, distinct from both Gate 3A classes: not an unexpressible clause, and
not an over-reach, but an expressible clause written with insufficient
discrimination.

That is the next iteration's problem, and it is deliberately not solved here.

The warm column is empty because the warm run was not run, and the code will
not fill it from theory. That is the Gate 3A finding applied to itself.

## Deferred

- Evidence Agent, Auditor, mutation generation, dashboard, locked evaluation.
- `estimatedCostUsd` stays null; no pricing rule exists.
- The clean-source guard is wired into the StateProof CLI only. The baseline
  CLI is left exactly as frozen, so its code path is byte-identical to the one
  that produced the frozen baseline.
- The measured warm run, which the cold guardrail failure blocked. The
  machinery for it is built and tested; it has simply not earned the right to
  produce a headline number yet.
- A defect in Gate 3B's own code, found after the run and left as it ran: the
  cold planner derives the contract run id from an option the CLI does not
  set, so this run's bundle was written to `artifacts/contracts/RUN-contracts/`
  rather than a run-scoped directory. It affects nothing in this result, and
  fixing it now would put the working tree out of correspondence with the
  commit the manifest records.
